# App map

The App map shows how a team's app fits together across all its repositories. It is made with [Floorplan](https://github.com/haydenschmitty/floorplan) (MIT): its extractor, builder and job definitions are vendored at `vendor/floorplan`, and its viewer is vendored in the dashboard repository at `dashboard/vendor/floorplan`. CoderHelm adds its own adapter around them and never edits the vendored files.

## How a map is made

- `worker/src/passes/app_map.rs` runs Floorplan the way its `workflow.json` and `docs/unattended.md` describe a run without an agent session. One step per `app_map` message:
  - `start`: reads each repository's default branch head. When no head moved since the last map, nothing is redone. Otherwise it packs every repository side by side, Floorplan's files from the last run and the vendored release, and runs `services/worker/floorplan/driver.mjs` in the run sandbox (CodeBuild, where Node already is): a scan for a first map, Floorplan's own `refresh.mjs` after that.
  - The worker then does the model job Floorplan's result asks for (`architecture`, `update_architecture` or `descriptions`), with the job's own instructions, references and schema from `workflow.json`, the read-only tools it names over the same snapshot, and `submit`, whose answer is checked against the schema (`common::app_map::check_answer`). Architecture uses the team's primary model, descriptions the light model; every call is metered under feature `app_map`.
  - `build`: writes the answers and builds, until the build passes and every file and endpoint is described (the workflow's own limits: 4 and 3 attempts).
- Screens a route picks by type (`services/worker/floorplan/coderhelm/screens/dispatch.mjs`): a dynamic or catch-all route (Next.js app and pages routers, Remix and React Router flat routes, SvelteKit, Nuxt, Astro, TanStack and Solid file routes, or any route Floorplan already lists from a React Router, Vue Router or Angular config whose address ends in a parameter or a splat) that renders one of many components chosen by a resolved type, through an object or `Map` from type to component, a `switch` on the type, or an `if` chain on it, in the route file or a few imports down. Each type is a screen of its own (`fw: "dispatch"`): named from its renderer or type in plain words, linked to the renderer's file and line (followed through imports, re-exports, barrels and lazy or dynamic imports), with the address the code gives that type (the resolver's checks on the address's segments, a table or `switch` from type to path template or prefix) or else the route's own pattern with the type named (`/(berth)/*`). `nav` keeps the type, the renderer, the route file and where the address was read (`urlFrom`); its evidence cites the renderer, the dispatch and the address. What is behind such a screen, and the journeys from it, follow only what its renderer's own code uses, so several renderers in one file stay apart. Tables of blocks or sections are parts of a page and are not screens. The lookups name them too: `dispatch` on a screen in `map_overview`, `map_find` (also by type or renderer), `map_screen` (also by name), `map_file` and `map_impact`, and a journey step that stands on one names it (`screen`) in `map_flow`.
- Journeys are traced after the map is ready, in passes of their own (`worker/src/passes/app_map.rs` `flows_step`, `app_map_trace.rs`):
  - Each build re-checks the stored journeys in the sandbox (`floorplan/coderhelm/flows.mjs` `prepare`). A step whose line moved is re-lined. A step whose screen or candidate a new extractor renamed or split is re-pointed to the one that cites its code, a screen by the renderer whose lines hold the step. An entry is traced again only when its code changed: its candidates and the content of the files they cite both differ from when it was traced (`flows.json` keeps each entry's files, and every file's content hash, in `code`). So a release that changes only the extractor keeps every journey and traces none.
  - The entries to trace go in this order: screens the last map didn't have (and the screens a split made), then entries whose code changed, then the rest.
  - Tracing costs at most $3 a pass and $10 a team a day (`flows-spend.json`). A pass that can't start one entry within what is left of the day doesn't read the code at all.
  - Each repository is read again at the map's heads, tried again with backoff within the pass (and after a rate limit's reset when it is a few seconds away). One that still can't be read waits in the todo's `unread`, retried on a later pass after GitHub's reset for a rate limit, or after a backoff from 5 minutes, doubling up to an hour. Only the journeys whose files are in it wait; every other journey is traced. The status names it (`unread`, and the page's line `journeys_note`) until it can be read.
  - One resume at a time (`flows-next.json`, `{seq, at}`): the only message that runs is the one whose turn is the schedule's `seq`, and not before `at`. Every other message (a duplicate, an older watchdog) is dropped. A pass ends by scheduling exactly one resume: at once when it ran out of time, a minute later when it made progress, at the budget's reset (UTC midnight) when not one entry fits what is left of the day, or at a waiting repository's retry time. A pass that made no progress never queues the next one sooner than 5 minutes.
- After a push to a default branch (a code graph update), a team that has a map gets an update queued two minutes later. Floorplan's refresh keeps every description whose file didn't change, so only new or changed files and endpoints are described again.
- The map (`floorplan/graph@1`) is kept in the bucket at `app-map/{team}/graph.json.gz`, Floorplan's own files at `state.tgz`, and the step's job at `job.json`; the build status is in the settings table (`AM#{team}`, `STATUS`).
- With each map the worker also writes the page's copy (`view.json.gz`: read-only, Floorplan's checks labelled, stored as JSON with `Content-Encoding: gzip`) and a small index (`index.json.gz`, `common::app_map::MapIndex`: the repositories' folders, every file path on the map, each repository's main part and Floorplan's checks with their places). A map written before these existed gets them from the gateway on its first read.

## How the page reads it

- `GET /api/app-map` never reads or sends the whole map. It answers with the build status, a signed GET for the page's copy (`graph_url`, 15 minutes; the browser reads it from the bucket and unzips it), the same bytes through the API for a browser that can't reach the bucket (`graph_fallback`, `GET /api/app-map/graph`, passed on unread), when the map was written (`graph_at`), and CoderHelm's overlays (`overlays`) placed with the index: Recent work (`recent`), and Health (`health.add`, the Floorplan checks to `drop` by id, and the `summary`). The page lays them over its copy (`dashboard/src/lib/app-map-load.ts`, the same as `common::app_map::apply_overlays`) and reads the map again only when `graph_at` changes.
- Recent work reads the plans' "why" eight at a time, for runs that are on the map only; Health reads its four sources at once.
- The data bucket's CORS allows `GET` and `HEAD` from the dashboard's origins (`infra/lib/storage-stack.ts`), next to the uploads' `PUT`.
- `cargo test -p common a_page_view` measures a page view on a made-up 4,000-file map (`APP_MAP_BENCH_GRAPH=<graph.json.gz>` measures a map on disk); `cargo test -p gateway a_page_view_of_a_large_map` does it through the handler.
- Chat and `/mcp` still read the whole map at their first lookup (`load_graph`): one read per question, and their lookups need the files, links and descriptions the index doesn't keep.

## What CoderHelm adds (`common/src/app_map.rs`)

- Recent work and Health in the map's own `recent` and `health.issues` fields, laid over the page's copy on the page, so Floorplan's viewer shows them natively. CoderHelm's findings are marked `source: "coderhelm"` and link to their pages; Floorplan's own checks are marked `Floorplan check`, and one at the same file and line as a CoderHelm finding is dropped.
- The page's copy: read-only (Floorplan's exported mode), with the sandbox's folder left out.
- Lookups for the read API (`/api/app-map/part`, `file`, `screen`, `search`).
- The map lookups Chat and `/mcp` share (`common::app_map::Lookups`: `map_overview`, `map_find`, `map_part`, `map_screen`, `map_file`). Chat offers them when the team has a built map and reads the map at the first lookup; a question about how the app fits together gets them first (`chat_understand`). Each lookup is a citable source linking to the App map page focused on its parts, and an answer that used them carries a mini map of those parts (`map` on the answer and its saved message). The App map page's Ask box asks Chat (origin `app_map`), so its questions are kept in the person's chats. On `/mcp` the same lookups are read-only tools under `code:read`.
- `map_impact` (`common::app_map::impact`): what changing one file, endpoint (`METHOD /path`) or part reaches, in one answer: callers in other repositories and in the same one, the screens that use it (app and signed-in gate), the journeys through it, the outside services it reaches or that call it, the cloud resources that deploy or start it, and the data links. Every item cites a `file:line`; each group holds at most 20 and counts the rest. Chat, `/mcp` (whose instructions say to call it before changing shared code or an endpoint) and runs offer it.
- Runs read the map too (`worker::passes::run_map`): the planner, the coder (and the CI fix, test fix, incident and alarm rounds that run through it) and the reviewer get the map's lookups beside the code graph's, read once per step. The planner's first message carries a short overview (at most 6,000 characters, about 1,500 tokens): the repositories, the parts and where the ticket's likely files sit. A plan whose files reach other repositories goes back once until design.md has an `## Affected elsewhere` section, and a citation there that isn't a place on the map is left out. The reviewer is shown each endpoint the diff changes that other repositories call, with each caller's `file:line` (at most 4,000 characters). No map, a map without the run's repository, or one older than 30 days: nothing is offered or said.
- The Knowledge page shows the map as a source (`app_map` on `GET /api/knowledge`): its state, when it was built, what it covers (counted at build time on the map's index: screens per app, outside services, cloud links, repositories) and, for admins, Build again through the one-at-a-time rebuild. It is not split into passages: runs and Chat look things up in it directly.

## Bumping Floorplan

1. `scripts/update-floorplan.sh floorplan--vX.Y.Z` here, and `dashboard/scripts/update-floorplan.sh floorplan--vX.Y.Z` in the dashboard repository (the same release). Each clones the tag, checks every copied file against the release's `CHECKSUMS.txt`, copies only the files used, keeps the licenses and records the tag in `VERSION`.
2. `node --test services/worker/floorplan/driver.test.mjs` runs the driver on the made-up harbor fixture with the new release. If the map's shape changed, it fails; regenerate the fixture with `node services/worker/floorplan/make-fixture.mjs` and fix the adapter until `cargo test -p common app_map` and `cargo test -p gateway app_map` pass.
3. In the dashboard: `npm run floorplan` and `npx playwright test e2e/app-map.spec.ts`.

CI runs the driver test on every pull request.
