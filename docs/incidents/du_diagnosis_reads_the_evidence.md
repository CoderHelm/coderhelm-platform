# du. `du_diagnosis_reads_the_evidence`

**What happened:** Someone pasted a production alarm into Chat: a load balancer target group's p99 response time over its threshold. Chat spent its lookups searching and reading the alarm definitions in the infrastructure repository, made one metric query and one log group listing, and answered with a guess followed by a list headed "Not checked (I ran out of lookups)": the target group's p99 and request count, the service's CPU, its logs for the minutes around the alarm, and the rest of a result that had come back cut off. Chat's answer loop ended every question after a fixed number of model turns and then told the model to say what it hadn't checked. The guess compared the downstream service's slow-call count with a busier hour's count instead of breaking latency down by path and lining it up with request volume. The real shape was one path that is slow all day and sets the p99 only when overnight traffic is low.

**The guarantee:** No count of lookups ends a Chat answer. The loop ends when the model answers and the checks in code pass; a generous ceiling on turns, calls and time guards cost, and an answer that outlasts the foreground goes on in the background: the asker sees that it is still being checked, the answer is kept as pending, and the finished answer replaces it in place. An answer that lists checks it didn't run is sent back to run them. An alert, an error or an incident reads as a diagnosis: the live tools go first, the note asks for the metric behind the alarm with its traffic, the service's logs for the window and its resource metrics, with latency broken down by path and lined up with request volume; code reads past a small allowance wait until that evidence is in; an answer that never read it goes back. A diagnosis that hedges goes back to run the lookup that settles it and to name the fix (the slow call, and a minimum request count on an alarm that fires on low traffic). A long result keeps its head and tail and says what was cut and how to narrow the lookup; an answer over a cut-off result it never followed up goes back. A senior asker gets the conclusion first, at expert depth, with no added hedging.

**Where it's enforced:** `common::chat_intent::{Intent::Diagnosis, is_diagnosis, Reading::senior}`, `common::chat_evidence::{EvidenceFirst, fit_result, says_unfinished, says_hedged}`; in the gateway, `chat_agent::{run, LIMITS, Background, FINISH_THE_CHECKS, ANSWER_NOW}`, `chat_understand::{Understood::limits, Understood::evidence_first, Understood::order, Understood::must_look}`, `brain::{is_live_tool, Keeper, keep_exchange}` and the diagnosis part of `brain::CHAT_SYSTEM`. The replay is `chat_eval_replay::offline_a_nightly_p99_alarm_is_traced_to_one_slow_path_and_low_traffic`.
