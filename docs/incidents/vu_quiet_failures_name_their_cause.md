# vu. `vu_quiet_failures_name_their_cause`

**What happened:** One install logged three failures every day that nobody could act on. The agent's memory-read counter failed on every run, logged only as "service error": its update named the attribute `reads`, which DynamoDB reserves, so DynamoDB refused it each time. A data source in the install's own account was refused `rds-data:BeginTransaction` on every daily check: the role's template grants that call only on the databases its stack names, and the stack the release keeps current in that account named none, while nobody is ever asked to update that role. The access stack that runs that update was weeks behind, and its card read "the deploy role may not make  yet", naming nothing. And gateway requests hit the Lambda's limit with nothing logged between START and END.

**The guarantee:** An AWS SDK error on these paths logs its kind: the service's own code, or how the request failed. No update, condition, projection, filter or key condition expression the services send names a DynamoDB reserved word without a `#name` placeholder; a test reads every one against AWS's published list. Every RDS and Redshift Data API call the code makes is derived from its call sites and must be allowed by both role templates. The release's reader update names, in DatabaseClusters, each database an AWS admin made CoderHelm's read-only user for (reading only the names of those users' secrets). The access card always says what is missing and that CoderHelm can't update the access stack itself, only an AWS admin can; an access stack still running an older reader update reads as pending, never applied. A gateway request that runs out of its invocation's time logs its method, its route's pattern (never the path's values), and where the time went (each AWS call it made and the ones still waiting), and answers 503.
