# bo. `bo_alarm_reads_its_evidence`

**What happened:** An alert route sends a WAF signature-drift alarm (a Count rule seeing crawler A get past a Block rule after it changed its JA4 or user agent) to the team's terraform repository, where the fix is a pull request that updates the block rule's match. The run ended `needs_input` with a long question asking a person to grant the team's read-only role WAF and Athena access, "Default if unanswered in 4 hours: Grant access". `wafv2:ListWebACLs` and `GetSampledRequests` were denied: the role's setup script never added any WAF read. The web ACL logs to an `aws-waf-logs-*` bucket with an Athena table, and nothing read it.

**The guarantee:** The role stack's template (`CoderHelmLogReader`) has the WAF reads and a WAF log group (`WafLogs`): read-only Athena queries over the Glue tables on `aws-waf-logs-*` buckets, with results written only under the workgroup's own results location. With those reads the run gathers the rule's matches before it plans (sampled requests, and the logs in S3 by JA4, JA3, user agent, accept language, path and cookie presence, over the last three hours) and goes on to its pull request. Without them the refusal is the install's one setup item, **AWS role reads**, with the role stack's one-click update ([cw](./cw_role_reads_arrive_by_stack_update.md)); the run names it in one line and goes on. The stop judge turns an ask or a hold for the role's reads into a proceed, the hand-back list doesn't carry it, and an access question never shows a default that can't happen.
