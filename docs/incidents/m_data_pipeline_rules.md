# m. `m_data_pipeline_rules`

**What happened:** A data-pipeline PR kept one column stable by no longer advancing `updated_at` on some update and upsert paths. Two incremental readers used that timestamp (a `MAX(updated_at)` watermark and a `GREATEST(...)` change key), so edited rows refetched every run and other changes stopped reaching the search index. It also picked a winner among sibling rows with different tie-breaks from the full sync, skipped records without a parent silently, and showed nothing on real data.

**The guarantee:** The plan check sends back a plan that changes how a cursor column is written without listing its readers, or picks a winner among rows without naming the other path that makes the same choice. Before the pull request, for every ticket kind, the checklist fails a cursor write that can stop advancing, names each reader code search finds that the plan leaves out, wants a test that the column still advances, fails an ordering key that differs from the other path's, wants a test with ties and nulls, and fails a skip over records that is silent or logs per row (one warning per run with the ids, counts in the summary). With a data source connected, the proof check holds a data change until the evidence lists the ticket's records and edge cases before and after, and the description shows them in Verification.
