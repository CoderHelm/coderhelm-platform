# fe. `fe_round_work_round_trips`

**What happened:** A pull request touched a route folder spelled `%5Fmarkdown`. Landing the fix round read that file back through a contents URL built with the path as it is; GitHub decoded `%5F` to `_` and answered 404 for a file that was there. The 404 was read as "its work branch wasn't there, so it had saved nothing", and the branch holding the work was deleted, twice. On two other pull requests a fix round ran out of its time budget three steps in a row; the run page said "Resume continues from there", but the next round reset the WIP branch to the pull request's head and did the same work again (20, then 17, then 4 checkpoint commits thrown away on one run).

**The guarantee:** Every contents URL percent-encodes each path segment and the ref (`clients::github::contents_url`), so a path holding `%`, `#`, `?`, a space or brackets is the file it names. A file GitHub won't give back is not a missing branch (`round::fault_of`): the WIP branch and its work are kept, and the CI fix loop deletes the branch only for a fault that calls for a clean start. A new CI or review fix round on a head where a round left unfinished work goes on from that WIP branch, told it is continuing (`round::carried`, `round::picks_up`); a head that moved since starts fresh.
