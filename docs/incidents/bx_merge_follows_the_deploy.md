# bx. `bx_merge_follows_the_deploy`

**What happened:** A person merged one of CoderHelm's pull requests hours after closing its run by hand. The merge kept the run closed and the pull request watch looked only at finished runs, so the merge commit's deploy was never watched. The release steps armed when the pull request opened waited on another service's deploy (a production job on merge with a path filter on that service's folder, which never runs for a web change); staging's deploy was not a step and the `v*` tag that deploys production was never asked for.

**The guarantee:** A merge is followed the same way whoever merged it and whatever the run's status: CoderHelm's merge and a person's both take the watch's deploy act, which watches the merge commit's deploy and follows the release. A deploy is the change's only when its workflow runs for the files the pull request changed, and a workflow named for its environment goes before one service's deploy. The release waits for staging, then prepares production by the repository's own path (the tag under one approval when the team asks for it, said once in one line). A release armed on the wrong deploy is pointed at the right one, keeping steps already done, and the sweep picks up merges already missed.
