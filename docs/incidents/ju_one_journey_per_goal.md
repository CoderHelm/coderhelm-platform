# ju. `ju_one_journey_per_goal`

**What happened:** After a catch-all route was split into one screen per type, a stored map could hold the same journey more than once: under numbered ids with different step counts, or once from the catch-all route and again from the renderer that replaced it. A retrace from a new or split screen added its journey without retiring the one it replaced, and near-identical journeys from different entries piled up.

**The guarantee:** Every journey names the entries it stands for (`from`). An entry's retrace replaces every journey from it, including one moved there from a split catch-all (`app_map_flows::merge`). A journey from a catch-all route names the screens it was split into (`split`), and a trace of one of them with the same goal retires it. Near-identical journeys are merged into the most complete one, and that is the one with the most steps on the map and cited. Journeys that share a title but differ are titled by how they differ, by where they start or by a step only one of them takes. No id is a numbered copy of a title. The sandbox applies the same rules (`flows.mjs` `dedupe`, tested on the same fixture), so a stored map is cleaned on its next build with no model call.
