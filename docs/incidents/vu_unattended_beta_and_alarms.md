# vu. `vu_unattended_beta_and_alarms`

**What happened:** A self-hosted install on the beta channel never took a beta by itself, and a broken install went unnoticed. Every release looked like a permission change: CloudFormation reports a Modify for each policy that names another part's output, because that value is known only after apply, even when the policy documents are byte for byte the same. The updater counted any IAM Modify, and a scheduled update that changes permissions waits for a person, so the hourly check never applied one. The maintenance window was one hour a week (or a day), so at most one of several daily betas could install. After an update the watch probed only the worker and the gateway; Chat runs in its own function with its own role, lost a grant, and refused every question for about a day while both stayed healthy. The alarms counted Lambda Errors, which stay at 0 because the services catch and log every error, so none moved.

**The guarantee:** A Modify counts as a permission change only when the resource differs once both sides are resolved the way the template resolves them: the running stack's parameter values before, the change set's after, and an import known only after apply keeps its running value when the parent feeds it the same way and its source output is the same. An Add, a real widening, and anything that can't be compared still wait for a person, as before. The release notes list the same comparison against the previous release. On the beta channel, `day: "any"` installs at any hour, at least `gap_hours` after the last install; the stable channel keeps its window. The watch asks the streaming function to make Chat's own calls (the member check every stream runs and each DynamoDB action its role is granted), and a refusal rolls the release back like a failed worker probe. Every install alarms on ERROR lines per function, GitHub rate-limit lines and Chat answers that failed, each as a share of the traffic, into the alerts topic.
