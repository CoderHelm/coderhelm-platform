# cr. `cr_red_on_every_branch`

**What happened:** A pull request's end-to-end check failed on a test it had edited, while a vendor portal the page embeds had just opened registration: the test was red on every branch, staging included. The failure comment named the test, its error and had a screenshot of the vendor's sign-in drawer. The run never compared the test with the base branch. A fix attempt wrote that another spec was "broken on main"; the supervisor then reverted seven of the pull request's own files to an older head, which failed the same way. The description kept "CI is failing" with a lint warning as the error and "Deferred: reverted 7 file(s)" after the work had come back, and the run wrote that it couldn't confirm what the test saw. Four other runs reverted their own work with no comparison, one for a cloud account's load balancer limit in the preview deploy.

**The guarantee:** Before a CI fix round the failure is read from its own report (test, error, screenshot, report link) and the failing test is run with the head's test code against the base branch's deployment and the pull request's preview; both results, and each failing check's result on the base branch's head, are kept on the run (`common::ci_repro`). The fixer gets all of it, the screenshot as an image. A revert of CoderHelm's own work needs a record on the head that shows the change makes a check fail; a failure red on the base too is fixed on the branch and said, never reverted. Nothing CoderHelm writes calls a failure the base branch's, flaky or not this change's without that record, or says a failure couldn't be confirmed while its report was read. The "CI is failing" section names its head and goes once the head moves or its checks show no failure; a revert's "Deferred" line goes once its files are back (`common::ci_lines`).
