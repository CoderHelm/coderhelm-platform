# jv. `jv_type_screen_shows_its_own_branch`

**What happened:** A website served most pages through one catch-all route, and a shared renderer file drew each kind of page by its type. The map listed one screen per type, but each one opened on the shared renderer file alone: the screen itself and nothing else, never the blocks, the data fetch or the requests of that kind of page. Its journeys stood on the same shared file, so every journey through those pages looked alike.

**The guarantee:** A screen a route picks by type stands on its own renderer (the map's symbol for it), and what is behind it is what that renderer's branch draws, its local helpers included, plus what the resolver's function for that type loads: the query, the client that fetches it and the outside service. The code that makes a service's client is linked to that service before its manifests and env files, so a content store's fetch reaches it. The map's lookups describe the renderer symbol and count it as its file for impact. Journey candidates for the screen stand on the renderer's card and reach what its loader fetches, and a stored journey's steps inside that renderer move onto its card on the next build, with no new trace.
