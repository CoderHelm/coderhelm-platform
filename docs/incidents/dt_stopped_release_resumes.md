# dt. `dt_stopped_release_resumes`

**What happened:** A few pull requests' release records sat for good with their production deploy at "approval" or "pending", while production already ran a later release tag that held their merges. Each release record is moved by a chain of delayed tick messages, one tick sending the next. When a chain stopped (an old bug, a lost message, a failed send, a crash), nothing resumed it: only a new merge on that same pull request armed it again. The release catch-up looks only at a default-branch head that no tag holds, so it skipped these records. And had a tick run, a production tag step waiting on its card would have asked again, or once approved cut a new tag, for a change already in production.

The first sweep found release records with a filtered scan of the settings table, capped at a number of pages. On a large settings table the capped scan never reached the records: the sweep reported nothing to resume on every run while records sat stuck, and each run read a large slice of the table for nothing.

**The guarantee:**
- The sweep never scans the settings table. Each save of a per-PR release record adds its team to a settings index (`INDEX#RELEASE_RUN`). The sweep reads the index, then each team's `RELEASE#` records by key, every page to the end, so a record is found however large the table is or how many records the team has. Release tag records share the prefix and are skipped. A team with no per-PR release record left is dropped from the index. The index rebuilds itself from one full scan a day, so records saved before it existed, or by a save whose index write failed, are found within a day.
- Every save of a release record says when its next tick is due. The review sweep, right after the release catch-up, resumes each record that still has work left and whose tick is more than 30 minutes overdue. A record written before that time was kept is judged by its last write. Finished, held, parked and closed records are left alone.
- A resume is one normal tick on a fresh chain. It is claimed against the record as the sweep read it, so two sweeps never both resume it, a tick that wrote in between wins, and a late tick of the old chain is dropped. GitHub's budget is asked first; a held budget leaves the record for a later sweep.
- A resumed tick that fails is not retried by its own chain (unless GitHub's budget asked it to wait); the sweep counts it. After three resumes in a row that got no tick through, the record is left with its last error. A tick that saves clears the count.
- When a release tag already holds the merge, the production tag step follows that tag's deploy run, records the tag and the outcome, and says it once on the run and its ticket, at the time the deploy finished. It never cuts a tag or asks a card for it, and a card asked before the change shipped expires. A merge that no tag holds yet goes the normal way: the team's batched release, or a card as the team's release settings say.
