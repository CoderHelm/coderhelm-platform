# dd. `dd_criterion_on_the_preview`

**What happened:** A ticket asked that a page's answers be in the HTML the server sends, so they show with scripts turned off and crawlers read them. The run rewrote the block as markup that needs no script, wrote unit tests that render the component on its own, and pushed. Nothing it ran fetched the preview's page as the server sends it. The page loads the block on the client only, so the served HTML still had none of the answers, and the preview's own check found it after the push ("the text is not in the server HTML"). The run that opened that pull request had started from an issue with an empty body, so the two-way proof had no criterion to prove, and the ready decision read "nothing to prove".

**The guarantee:** The criteria to prove come from the ticket, else from the plan's criteria map (`common::e2e_proof::criteria_or_map`), so an empty ticket body never means nothing to prove. A criterion about what the server sends (the page source, the page with scripts off, what a crawler reads: `Criterion::about_served`) is also proven on the served page itself. CoderHelm fetches the criterion's page as the server sends it, on the preview and on staging, with a plain request and no script run (`e2e_proof::served_legs`, through `web_check::fetch_page`), and judges each side against the criterion. Not shown on the preview is coder work whatever the browser test says: it goes back as a fix round and the ready decision waits for it (`common::e2e_proof::outcome`, `standing_of`). Shown on the preview and missing on staging is proven. A side that couldn't be fetched or judged is labelled unverified with why, never a pass.
