# cp. `cp_criteria_proven_both_ways`

**What happened:** A ticket asked for one thing: on a library's slots page, the wing filter showed two Guest-Wing chips and should show one. The run wrote hundreds of lines of unit tests in several files and never loaded the page the ticket names. Nothing ran on staging or the preview, so nothing showed the chip was doubled before or single after. It also added three helpers to one file in the same change, two of them copies of the same first-per-key filter, with no shared logic. A person later replaced them with one helper, cut the unit tests and added the one end-to-end test of the page. Across the runs audited with it, many pull requests whose ticket named a page had no end-to-end spec, and most of those that changed one never ran it on staging.

**The guarantee:** The plan maps each criterion that names a page or what a person sees to an end-to-end test of that page, with its assertion (`## Criteria map`). A plan without one, or with a unit test in its place, is sent back (`plan_shape::criteria_gaps`). Before the pull request is called done, each criterion's test runs on staging and on the preview through the red-check runner (`ci_repro::two_way`). Both results are kept on the run and written into the pull request (`common::e2e_proof`, `e2e_proof`). Failing on staging and passing on the preview is proven. Passing on both, failing on the preview, or having no test goes back to the coder, and the ready decision waits for it. A side that couldn't run is labelled unverified with its reason. Near-identical helpers added in one change are compared with each other (`minimal_change::twin_helpers`), and the coder's guard refuses the second until the edit names what they share (`explore_guard`, `shares`).
