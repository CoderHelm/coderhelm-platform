# dc. `dc_one_run_per_ticket`

**What happened:** A tracker ticket started a run. Seconds later a person approved a plan written for that same ticket, and the plan's task opened a GitHub issue for it, labelled for CoderHelm. The issue started a second run. The two runs carried different ticket ids (the tracker key and `GH-<n>`), so every guard keyed by ticket id saw two tickets. One ticket got two runs, two branches and two pull requests, and both runs spent their budget on the same change.

**The guarantee:** Every fresh run takes one claim on its ticket's canonical key before it writes anything, at the run start that every trigger goes through (`common::one_run`, `passes::one_run::claim`). The key is the ticket the run is for, not the event that carried it in. An issue CoderHelm opens for another ticket names that ticket twice: in a marker in its body and in the stored link from the issue to its plan task. Its run therefore resolves to the ticket's own key. A second trigger for a ticket that a live run holds starts nothing, from any source and in either order, and the live run's page says the ticket arrived again. A run that has ended hands the claim to the ticket's next run. A plan task written for a ticket that a live run already works opens no issue: it is linked to that ticket and run.
