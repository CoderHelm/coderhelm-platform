# pl. `pl_plan_follows_the_work`

**What happened:** Two plans read wrong for weeks. In the first, a person approved one of three draft tasks from its row, as the page suggested. The worker filed its ticket, marked the task done and, with no task waiting on another, marked the plan done. The page hid the Approve buttons once a plan was not a draft, so the other two tasks stayed drafts with no way to start them, under a plan that said Done. In the second, all four tasks were filed and read done, and so did the plan, while one pull request merged, one closed unmerged, one run failed with no pull request, and one task took eleven runs and seven pull requests (about $130) without merging. No run or pull request was ever written back to a task.

**The guarantee:** A task's state is derived from the runs of its ticket and their pull requests, never from filing the ticket (`common::plan_state`): Draft, Queued, Working, Needs you, Failed (with its reason), In review, Merged or Dropped. The plan's state comes from its tasks, and it is Done only when every task merged or was dropped. A refresh (`common::plan_sync`) links each run to its plan and task and writes the states; it runs on every run status change, on pull request events, on approval and on the plan page, and the plans list refreshes plans written before it (the backfill). Approving one task never ends the plan: the drafts left are listed as something a person has to approve or drop.
