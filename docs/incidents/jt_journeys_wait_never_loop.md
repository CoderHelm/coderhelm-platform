# jt. `jt_journeys_wait_never_loop`

**What happened:** A release that changed the map's extractor retraced every journey, and earlier rebuilds that day had already spent most of the day's tracing budget. Each journeys pass then found that not one entry fitted what was left, traced nothing, cost nothing, and queued the next pass a minute later, while the watchdog each pass also queued piled up beside it, so the step ran every half minute for minutes with no progress. Then GitHub refused one repository's tarball once (a 403). The whole trace gave up and wrote every journey from the untraced candidates, so the journeys through the new screens were mostly missing.

**The guarantee:** A repository GitHub won't give is tried again with backoff within the pass (`app_map_trace::read_repo`). If it still fails, only the journeys that need it wait (`split_ready`), and every other journey is traced. The status names the repository in one plain line (`common::app_map::unread_line`), which clears itself once the repository can be read. The waiting journeys are tried again on a later pass, after GitHub's reset when the refusal was a rate limit (`note_unread`). A pass that can't go on, because the budget is spent or every entry waits on a repository, schedules exactly one resume, at the budget's reset or the retry time (`next_resume`). Every other message is dropped (`take_message`), and a pass that made no progress never queues the next one sooner. A release that changed only the extractor keeps every journey and traces none, because each entry remembers the code it stands on by content (`flows.mjs` `prepare`). Steps on a renamed or split screen are re-pointed by their lines.
