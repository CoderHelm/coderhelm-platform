# sg. `sg_sign_in_outage_retries`

**What happened:** A knowledge source on a hybrid install stopped syncing for hours and asked its team to reconnect, though its sign-in was fine. One scheduled sync asked the hosted broker for a token while the provider's sign-in server was briefly unavailable. The broker sent that passing failure to the install as `invalid_grant` with HTTP 400, its reason written as a debug dump of the connection error. The install took `invalid_grant` as a revoked grant and marked its connection as needing a reconnect, so every scheduled sync after it stopped at once on that stored mark, each one asking the team to reconnect the source. The next check after a person signed in again worked.

**The guarantee:** Only a definitive refusal asks a person to reconnect: HTTP 400 or 401 with `invalid_grant`, `invalid_client`, `unauthorized_client`, or the provider's revoked or expired refresh signal (`oauth::TokenError::needs_reconnect`). No answer, a timeout, a `429` or a `5xx` is passing, whatever its body says. A passing refusal is asked again within the run with a short backoff, then left for the next sync, and the stored tokens are never marked or wiped. The same holds when the key service can't open the saved tokens for a moment. The broker answers a passing failure as `temporarily_unavailable` with HTTP 503 (`hybrid::broker_refusal`). A sync that ends on a passing cause is recorded as "retrying", the source keeps its status, and the page shows the cause once with how many syncs in a row and since when. A sync that finishes clears it. Only one refresher at a time sends a refresh token (`Store::claim_refresh`), and another one waits for its tokens, so two syncs can't spend a rotating refresh token twice.
