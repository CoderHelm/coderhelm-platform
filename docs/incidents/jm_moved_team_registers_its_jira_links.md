# jm. `jm_moved_team_registers_its_jira_links`

**What happened:** A team moved from hosted CoderHelm to a self-hosted install and kept its team id, and its Jira site stayed linked to that install through CoderHelm. The site's Jira app registers its links with CoderHelm under that id, and CoderHelm looked the team up first. It holds no team record for a team that moved, so every registration was refused as "team not found" (404). The app turned that into a 502 for the install's request to register again, and the install logged only the status. The hosted Jira record, which CoderHelm's proxy and the install's copy read, never gained the ticket lookup link, so chat on the install couldn't read tickets. The site's events still reached the install, because the intake routes them by the link without the team record.

**The guarantee:** A registration for an id with no team record but a standing link (route and link both, the same test the Jira intake makes before it relays an event) is the linked team's. It is checked against the secret on its hosted record in constant time, validated like any registration, saved on that record with the site and the app's version, and answered 200. Nothing goes to the install: it keeps its proxy links, and copies again by itself once the triggers CoderHelm reports change. An id with neither a team record nor a link is still not found. When the app refuses a request to register again, the log carries the app's answer (its `error`, capped).

**Where it's enforced:** `common::jira_connection::{Registrant, refusal_words, registered, copy_is_stale}`; in the gateway, `api::forge_register_urls`, `hybrid_jira::{standing_route, relay_team}`, `jira_heal::heal`, and `hybrid_install::{jira_sync_plan, refresh_jira_copy}`.
