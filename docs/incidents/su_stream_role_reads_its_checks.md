# su. `su_stream_role_reads_its_checks`

**What happened:** Right after the Require single sign-on release, Chat stopped working on a self-hosted install. Every question in Chat, and every Ask on the App map, answered "Your session ended. Sign in again.", and signing in again changed nothing. The streaming function logged `Member record not read; request refused`. The release made each chat stream check the session its token was minted from, which reads the member's record from the users table. The chat streams run in their own Lambda, whose role grants table by table and had no grant on the users table, so every read was refused. The main gateway, which can read every table, passed every test. The brain stream then reported the failed read as an ended session.

**The guarantee:** The streaming function's role reads the users table, and the teams table that a refusal names. `infra/streaming-dynamodb.json` lists every DynamoDB call the two stream routes make. The gateway's tests record those calls by driving both routes against the AWS stand-in, for hosted and self-hosted installs and for every kind of session, and fail when a call isn't listed. The infra tests synthesize the streaming stack and fail when its role doesn't allow a listed call. A member record that can't be read is a server problem: Chat answers "Chat couldn't check your sign-in right now. Try again." with a 503, and only a session that really ended says `session_ended`.

**Where it's enforced:** `infra/lib/streaming-stack.ts` (the grant), `infra/streaming-dynamodb.json`, `infra/test/streaming-access.test.ts`, `services/gateway/src/routes/stream_access.rs` (with `fake_aws::Store::dynamo_calls`), and `routes::brain::scoped_refusal`.
