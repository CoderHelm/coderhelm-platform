# vq. `vq_two_repo_ticket_runs_end`

**What happened:** Two related tickets touched two connected repos: a setting in an infrastructure repo, and the web page that reads it. The infra ticket named its repo. Routing picked that repo, then the plan's repo check counted more mentions of the web repo and moved the run there. With nothing real to change, the run built a large end-to-end test as stand-in work. Its own review called the test out of proportion; the fix round's cut was judged out of scope twice, and a quoted template line from the review ran as the test command. The planned-work check then asked for the full test again, the round that tried was refused for undoing the review's fix, and the run failed into a hand-off with an unknown error. The web ticket's run planned the infra change as a step no executor could do, waited on a workflow its label never started, with no end, kept an old head's pending checks, said nothing was needed from anyone, and logged the missing Actions permission once per workflow run.

**The guarantee:** A repo the ticket names (a `Repo:` line, or a title naming one connected repo) is the run's repo, and the repo check never moves it. A change the plan puts in another connected repo is that repo's linked pull request in the same run; a step asking for a pull request elsewhere is never run on this one. Removals a review comment asks for are kept, and a quoted template is never a command. What CoderHelm's review settled (it asked for less, or a later round was refused for undoing its fix) is not planned work left, so the plan and the review never stall each other. Every outside wait ends at a limit (30 minutes for a run to start, 6 hours for it to end, a day for an approval) or when the pull request merges or closes, and the run says what it waits on and until when. The CI wait follows the current head. A missing Actions write permission is one status on the run and one install item, and no re-run is tried without it.
