# vp. `vp_waits_for_the_change_it_builds_on`

**What happened:** A ticket flipped a flag in a file that another ticket's run was still creating, and that run hadn't merged. The planner saw it correctly: the file and what it configures didn't exist yet in any environment. The plan check then rejected the plan as a change outside the code that leaves nothing for a person and waits for nothing, planned again at a cost, and ended the run failed. It did wait for something: the other ticket's change.

**The guarantee:** Before the plan check rejects anything as waiting for nothing, it looks for the change that makes the ticket's target: a ticket the planner's cause names, else one the ticket or its links name, with its run and open pull request when the team has them. With one, the run waits for that change: the dependency is kept on the run and shown on its page, the ticket hears one note ("Waiting for ... to merge; this run continues by itself after that."), and it is never a failure or a plan-check failure. A merge (its webhook, and the 15-minute sweep) plans again against the new base and goes on; nothing is planned before then and the note is never repeated. If the dependency's run stopped, the page says so and the self-heal sweep resumes that run. A dependency closed without merging gives one note and stops the run as "needs you" with that reason. Runs left failed this way before the release are set waiting by the self-heal sweep.
