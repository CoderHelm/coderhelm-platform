# vs. `vs_retry_starts_in_the_named_repo`

**What happened:** A ticket named its repo, an infrastructure repo, on a `Repo:` line. An earlier run had been moved by the plan's repo check to the connected web repo and opened a pull request there full of stand-in work. After routing learned to keep a run in the repo the ticket names, a person pressed Retry on that run. The retry routed to the named repo, then took up the earlier run's cached plan as final, so the guarded repo check never ran. A second switch, the one made before implementing when the plan's files are in another repo, had no such guard and moved the run back to the web repo. There the multi-repo path found the earlier run's open pull request and the stand-in work went on. Nothing had closed that pull request.

**The guarantee:** No repo switch ever moves a run off the repo the ticket names; work the plan puts in another connected repo goes there as that repo's linked pull request. A Retry of a run that worked in another repo than this run's starts over here: a new plan, none of the earlier run's finished work, and the ticket's branch already in this repo kept with its commits rather than reset or made twice. When the ticket names this repo, CoderHelm's own pull request the earlier run left in the other repo is closed once, after the agent-permission check (`close_pull_request`), with a short note naming the ticket's repo; its branch is kept, and nothing is written to the ticket.
