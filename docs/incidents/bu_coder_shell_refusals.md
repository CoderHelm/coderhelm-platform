# bu. `bu_coder_shell_refusals`

**What happened:** A coding run needed to know whether a vendor's page could be shown in an iframe (its `X-Frame-Options` and `frame-ancestors`) and what the vendor's embed script did. The coder sent `curl -sI <page>` and `curl -sS -m 20 <script>`; both came back "Not allowed: not a command for here", and the reason reached the run page only after the step was saved. A week of runs showed the same wall for other shapes: reads chained with `;`, `git show`/`git log`, and `corepack enable && pnpm install && <test>` chains. Meanwhile every `pnpm ...` command the sandbox did run ended with exit 127 after about 36s: the sandbox ran the bare command, with no install and no pnpm, and the coder sent the same command again and again.

**The guarantee:** A read-only `curl`/`wget` is a page fetch with the page tool's safety checks, returning the status, every header and part of the body; one that writes, sends data or credentials is refused with the reason and the read-only form. Chained reads run as their tools; chained sandbox commands run as one build with each part asked of the gate; git history reads run as the history tool. A sandbox command runs after the repository's install, and a program the sandbox still lacks is diagnosed once, with the routes that work, and never built for again in that step. Every refusal names what to use instead, and the run log's line says which refusal it was.
