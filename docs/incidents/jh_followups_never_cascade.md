# jh. `jh_followups_never_cascade`

**What happened:** CoderHelm files follow-up tickets from a Jira ticket's findings (see `jf_followups_filed_not_asked` and `jg_followups_once_per_topic`). Each follow-up was labelled `coderhelm`, `coderhelm:<repo>` and `coderhelm:followup:<source>`. `coderhelm` is the default trigger label, and on that trigger every label starting `coderhelm:` counts too. So every follow-up started its own run, each of those runs filed follow-ups of its own, and some of the runs did the same work as others.

**The causes:**
- Follow-ups were filed with the same labels a person uses to hand CoderHelm a ticket.
- Nothing told a follow-up from any other ticket at the trigger, and nothing stopped a run on a follow-up from filing more.
- Nothing limited how many follow-ups one source could produce in a day.

**The guarantee:**
- A follow-up is filed with `coderhelm-followup` and `coderhelm:followup:<source>` only. CoderHelm reads the team's trigger label from its Jira settings and never adds a label that trigger matches. No repository label is added (on the default trigger it is a trigger too), and no assignee is set. The Jira app keeps only follow-up labels on a follow-up, whatever CoderHelm sends.
- A follow-up label is never a trigger, whatever the team's trigger label is.
- The Jira webhook starts no run on a ticket CoderHelm filed as a follow-up. It knows one by its `coderhelm:followup:` or `coderhelm-followup` label, by CoderHelm's own record of it (`FOLLOWUP_OF#<key>` in the settings table, written when it is filed), or by the sentence every follow-up's description ends with. This holds even when a person adds the trigger label or assigns CoderHelm by hand. The first time, CoderHelm comments on the ticket that it is a follow-up and that a person starts it from CoderHelm: Start a run with the ticket's key (the dashboard, or `start_run` in a connected app). That start reads the ticket from CoderHelm's record.
- A run on a follow-up files no follow-ups of its own (depth one). Its drafts go in its comment instead.
- One source ticket files at most 10 follow-ups a day (UTC), across every run on it, counted atomically. A draft past that is not filed, and the comment says why.

- Duplicates close themselves. The follow-ups of one source (its whole family: filed from it, and from those) are read together with their latest runs. A pair closes only when the small model check reads it as the same work and the follow-up topic matcher (`followup_tickets::near`) finds the two near, the topic key filing uses. A pair the matcher reads as the same and the check doesn't, or the check reads as the same and the matcher finds unrelated, is flagged on both tickets, and so is a pair taking opposite approaches to the same code (fix the components, delete them); neither ticket of a flagged pair is closed. In each group CoderHelm keeps one ticket, decided once and recorded, and never a closed one (`wa_duplicate_keeper_stays`): one whose run finished, else one with code and a pull request, else the earliest. Every other run paired with it is closed with a person's close steps (the status, the ticket lock, auto-merge, the Jira note); its pull request closes through the agent-permission gate with a note naming the keeper's pull request, its branch kept, and never when a person committed to it or asked for changes. The Jira note says "Duplicate of KEY (topic). Closing; the work continues there. Closed by CoderHelm." Each close is logged (`FOLLOWUP_CLOSE_LOG#`), and one source closes at most 10 a day.
- It runs by itself: on the worker's scheduled tick, each team at most once an hour (the first tick after a deploy included), over the families with more than one run or pull request still open. It also runs when a person starts a follow-up from CoderHelm (one its family already covers is not started), and with `POST /api/followups/dedupe`.

**Where it's enforced:** `common::followup_tickets` (`labels`, `is_trigger_label`, `is_followup_label`, `source_of_labels`, `source_of_body`, `of_record_sk`, `day_record_sk`, `DAILY_CAP_PER_SOURCE`, `held_comment`, `depth_refusal`); in the gateway, `trigger_gate::is_trigger_label`, `jira_webhook::{process_jira_payload, followup_record, hold_followup}` and `run_start::{jira_ticket, followup_message}`, `followup_dedupe::{sweep, root_of, dedupe}` and `run_close::close_as_coderhelm`; `common::followup_dedupe` (`decide`, `agreed`, `plan`, `rank`, `close_comment`, `flag_comment`); in the worker, `passes::followups::{file, followup_source, take_daily_slot, keep_followup_of}` and `passes::followup_dedupe::{sweep, families, worth_reading, close_duplicate}`; in the Jira app, `followups.followupLabels` and `followups.repoOfLabels`.
